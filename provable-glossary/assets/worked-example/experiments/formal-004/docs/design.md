# 時間制限つきチケット販売の設計書

## 1. 目的

この仕組みは、上映回の座席をオンラインで販売するときの流れを定めます。対象は次の 3 点です。

- 座席の仮確保に有効期限があること
- 外部の決済サービスとのやり取りに時間がかかること
- 販売の途中で、サイトが緊急メンテナンスに入る場合があること

顧客が座席を押さえ、決済し、入場権を受け取るまでの流れを決めます。あわせて、時間切れ・決済失敗・メンテナンスが重なったときに座席と決済をどう扱うかを決めます。

議論を単純にするため、上映回は 1 つ、座席は 1 席、顧客は 2 人に限定します。

## 2. 時間の扱い

時間は「単位時間」ごとに区切って進めます。時間の経過を意味するのは、単位時間が 1 つ進む出来事 (tick) だけです。それ以外の出来事は、時間を消費せずに起きます。

どの時点でも、条件を満たす出来事のうちどれが次に起きるかは決まっていません。ただし、すぐに処理すべき事柄が残っている場合は時間を進めません。詳しくは「6. 時間の進み方」で説明します。

## 3. 調整項目

運用によって値を変える項目は次のとおりです。値はここでは決めず、名前で参照します。

| 名前 | 意味 |
|---|---|
| TTL | 座席を仮確保したときに与える有効期間 (単位時間の数) |
| EXT | 決済を始めたときに、仮確保の残り時間へ足す延長分 |
| LAT | 決済サービスが結果を返すまでにかかる最大の単位時間 |
| MAINT | 緊急メンテナンスが続く最大の単位時間。0 の場合、緊急メンテナンスは起きない |
| FREEZE | 有効にすると、メンテナンス中は仮確保の残り時間を減らさない |
| REACQUIRE | 有効にすると、仮確保を失った顧客の決済成功を処理するときに、座席が空いていれば座席を取り直す |

## 4. 登場するもの

### サイト

販売サイトは「稼働中」か「メンテナンス中」のどちらかです。メンテナンス中は、メンテナンスに入ってから経過した単位時間を記録します。緊急メンテナンスは販売期間中に 1 回しか起きないので、すでに起きたかどうかも記録します。

### 座席

座席は次の 3 つの状態のどれかです。

- **空き**: 誰も押さえていない。
- **仮確保中**: ある顧客が押さえている。どの顧客が押さえているかと、残り時間を持つ。
- **販売済み**: ある顧客に売れた。どの顧客に売れたかを持つ。

### 顧客ごとの決済状況

顧客ごとに、決済の進み具合を次のどれかで持ちます。

- **未決済**: 決済をまだ始めていない。または、一度失敗して元に戻った。
- **応答待ち**: 決済サービスに依頼して、結果を待っている。依頼してから経過した単位時間を持つ。
- **成功・処理待ち**: 決済サービスから成功が返ってきたが、販売側の処理はまだ済んでいない。
- **入場権発行済み**: 座席が確定し、入場権を受け取った。
- **返金済み**: 決済は成功したが座席を渡せず、返金した。

入場権発行済みと返金済みは最終状態です。この 2 つの状態になった顧客は、それ以降の手続きには進みません。

### 初期状態

販売開始時の状態は次のとおりです。

- サイトは稼働中
- 座席は空き
- 2 人の顧客はどちらも未決済
- 緊急メンテナンスはまだ起きていない

## 5. 処理の流れ

### 座席の仮確保

顧客が座席を押さえる操作です (reserve)。次の条件をすべて満たすときに受け付けます。

- サイトが稼働中である
- 座席が空いている
- その顧客が未決済である
- まだ誰も入場権を受け取っていない

受け付けると、座席はその顧客の仮確保中になり、残り時間は TTL になります。

### 決済の開始

仮確保した顧客が支払いを始める操作です (startPayment)。次の条件をすべて満たすときに受け付けます。

- サイトが稼働中である
- その顧客が未決済である
- その顧客が座席を仮確保していて、残り時間が残っている

受け付けると、仮確保の残り時間に EXT を足します。顧客は応答待ちになり、経過時間は 0 から数え始めます。

### 決済サービスからの応答

決済サービスは、依頼から 1 単位時間以上たってから結果を返します。遅くとも LAT 単位時間までには必ず返します。応答はサイトとは独立して届くので、メンテナンス中でも届きます。

- **成功の応答** (providerSucceeds): 顧客は成功・処理待ちになります。座席の状態はこの時点では変えません。
- **失敗の応答** (providerFails): 顧客は未決済に戻ります。その顧客がまだ座席を仮確保している場合、仮確保を解放して座席を空きに戻します。仮確保がすでに切れていれば、座席はそのままにします。未決済に戻った顧客は、もう一度仮確保からやり直せます。

### 決済成功の処理

成功・処理待ちの顧客について、販売側で結果を確定させる操作です (settle)。サイトが稼働中のときだけ行います。メンテナンス中に届いた成功は、復旧するまで処理待ちのまま残ります。

処理では、まずその顧客に座席を渡せるかを判断します。次のどちらかに当たれば、座席を渡せます。

- その顧客が座席を押さえている
- REACQUIRE が有効で、座席が空いていて、まだ誰も入場権を受け取っていない (取り直し)

座席を渡せる場合は、座席を販売済みにして、顧客に入場権を発行します。渡せない場合は、座席の状態を変えずに、顧客へ返金します。

### 緊急メンテナンスの開始と復旧

脆弱性が見つかると、サイトは緊急メンテナンスに入ります (detectVulnerability)。これが起きるのは、次の条件をすべて満たすときだけです。

- サイトが稼働中である
- MAINT が 0 より大きい
- 緊急メンテナンスがまだ一度も起きていない

メンテナンスに入ると、経過時間を 0 から数え始めます。

メンテナンスは少なくとも 1 単位時間続きます。そのあとサイトは稼働中に戻ります (recover)。経過時間が MAINT に達すると時間はそれ以上進まないので、遅くともそこで復旧します。

メンテナンス中にサイトで行えない操作は、仮確保・決済の開始・決済成功の処理です。決済サービスからの応答だけは、メンテナンス中も届きます。

## 6. 時間の進み方

単位時間が 1 つ進むと、次の変化がまとめて起きます。

- 応答待ちの顧客は、それぞれ経過時間が 1 増えます。
- メンテナンス中は、メンテナンスの経過時間が 1 増えます。
- 座席が仮確保中なら、残り時間が 1 減ります。残り時間がなくなった時点で仮確保は切れ、座席は空きに戻ります。ただし、FREEZE が有効でサイトがメンテナンス中の場合は、残り時間を減らしません。

仮確保が切れても、その顧客の決済状況は変えません。たとえば応答待ちの顧客は、仮確保を失ったあとも応答待ちのままです。

次のどれかに当たるときは、時間を進めません。先に該当する出来事が起きる必要があります。

- サイトが稼働中で、成功・処理待ちの顧客がいる。この場合は先に決済成功を処理します。つまり、稼働中に届いた成功は時間を置かずに処理されます。
- 応答待ちの経過時間が LAT に達した顧客がいる。この場合は先に決済サービスが応答を返します。
- メンテナンスの経過時間が MAINT に達している。この場合は先にサイトが復旧します。

## 7. 決まりのまとめ

- 座席は 1 席なので、仮確保できる顧客は同時に 1 人だけです。誰かが入場権を受け取ったら、それ以降は新しい仮確保を受け付けません。
- 仮確保の有効期間は TTL です。決済を始めると EXT だけ延びます。残り時間がなくなれば、仮確保は自動的に切れます。
- 決済の結果は、依頼から 1 単位時間以上、LAT 単位時間以内に返ります。
- 決済の失敗は、顧客が持っていた仮確保を解放し、顧客を未決済に戻します。
- 決済成功の処理はサイト稼働中だけに行います。稼働中は成功が届いた時点ですぐに処理します。
- 決済成功を処理するとき、座席を押さえていれば入場権を発行します。押さえていない場合は、取り直しが有効で、かつ取り直せる状況であれば入場権を発行します。どちらでもなければ返金します。
- 緊急メンテナンスは販売期間中に最大 1 回です。1 単位時間以上、MAINT 単位時間以内続きます。メンテナンス中に仮確保の残り時間を止めるかどうかは FREEZE で切り替えます。
