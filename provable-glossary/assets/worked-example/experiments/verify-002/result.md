# 検証実験 002 の結果

手順は [protocol.md](protocol.md)、採点は [scores.tsv](scores.tsv)、対照の答えは `answers/` にある。

## 結論

**この大きさのモデルでは、形式手法は検証の道具としての価値も示せなかった。**
道具を使わない対照は、3 つのモデルとも全問を正解した。事前に決めた基準
(どれかの対照が 16 問中 15 問以上を正解したら、価値は示せなかったと結論する) に当たる。

## 数字

| 対照 | 乱数で選んだ 16 問 | 難問 3 問 |
|---|---|---|
| Fable 5.2 | 16 / 16 | 3 / 3 |
| Opus 5.5 | 16 / 16 | 3 / 3 |
| Sonnet 5.5 | 16 / 16 | 3 / 3 |

- 「破れる」の 11 問は、対照が出した操作の列を Quint で実行して、性質が実際に破れることを確かめた。
- 採点器は、実行できない列、性質を破らない列、成り立つ変種への列を、どれも不正解にする。確かめた。
- 難問 3 問は、シミュレータが 3000 回の試行で反例を見逃した組である。
  対照は 3 つとも、9 手の反例を書いた。

## 予想との照合

- 外れた: Sonnet は 12 問前後、誤りは見逃しの側に多い、と予想した。誤りは 1 つもなかった。

## 何が言えて、何が言えないか

言えること:

- 到達可能な状態が数百で、性質の成否がスイッチ 1〜2 個で決まるモデルなら、
  モデル検査器はモデルの読解に対して正確さの上積みを持たない。
- 目的を持って反例を探す読解は、無作為のシミュレーションより強かった。

言えないこと:

- 対照が読んだのは Quint の仕様である。設計を形式的に書く作業は、対照の側も使っている。
  この実験が比べたのは「検査器」と「読解」であって、「形式化する」と「しない」ではない。
- 「成り立つ」という対照の答えは、当たっていたが、証明ではない。TLC は全状態を調べた。
- モデルが大きくなったとき、性質が多くの選択肢の組み合わせで決まるときに、
  対照がどこで誤り始めるかは分からない。

## 残る違い (正確さ以外)

| | TLC | 対照 (モデルの読解) |
|---|---|---|
| 1 問の時間 | 約 0.4 秒 (起動を含めて数秒) | 数十秒〜数分 |
| 同じ問いへの答え | 毎回同じ | 保証がない |
| 「成り立つ」の根拠 | 全状態を調べた | 推論。検証できない |
| 変更のたびの再検査 | `just check` で自動 | 毎回やり直す |

## 限界

- モデルは小さく、性質は単純である。正解表を見た時点で分かっていた。
- 安全性だけを扱った。活性は扱っていない。
- 対照は同じ系列のモデルで、各問 1 回である。
